# What I cut and why

I intentionally cut provider-specific structured-output APIs, constrained decoding, streaming JSON, observability, schema evolution, deeply nested models, and model benchmarking. All of those are useful topics, but they would make the course wider without helping the learner reach the capstone faster. I wanted the course to stay centered on the core production failure mode: a model returns output that is parseable but still unsafe for application code. The two lessons therefore focus on parsing, schema validation, diagnostics, repair prompts, bounded retries, and explicit failure. I also kept the learner build offline and fixture-driven so the reviewer can reproduce the exact behavior without an API key. That makes the build deterministic and keeps the technical progression easy to inspect. The tradeoff is that the course teaches a general repair pattern rather than every provider-specific feature available in production systems.

# Where the course is weakest

The weakest part of the course is that the learner build uses cached model responses rather than a live model during the repair loop. This is intentional so the submission can run offline and produce deterministic output, but it means the learner does not see the full variability of real model failures. In production, a repair attempt may introduce a new schema error, return prose again, or partially fix the original output while breaking another field. The cached fixtures demonstrate successful repair and bounded failure, but they cannot reproduce that entire range of behavior. The course also does not explore more advanced concerns such as repair-loop telemetry, latency tradeoffs, schema versioning, or provider-native constrained decoding. Those would be the next topics I would add in a longer course after the learner has a reliable validation boundary and bounded repair strategy in place.
